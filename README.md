# Roomform

An interior design studio built with TanStack Start + Router, React, Vercel AI SDK, and direct OpenAI image editing. Hosted as one Railway Node service with SQLite on a persistent volume.

Create a room, upload listing/camera photos, collect product photos or IKEA links, select references, and generate or refine a photorealistic visualization — from photos, a 3D guide, or freestyle with no photo at all. Original architecture remains the prompt's authority. Results include history, downloads, brush edits, before/after videos and a before/after slider.

Upload overlapping room photos, open **3D room**, and click **Build 3D room**. The server runs classical COLMAP DSP-SIFT extraction with affine feature shapes, guided brute-force matching, and structure from motion on the CPU. Two-view tracks are retained so small listing-photo sets can initialize. No wall labels, room measurements, AI models, external image services, or OpenAI key are needed. The saved preview contains recovered colored points and camera positions; orbit it or select a recovered photo angle. This is a sparse, partial reconstruction. Blank walls and unseen areas remain gaps, and the result has no known physical scale. It is not a solid, textured mesh or a measurement tool. Listing photos may fail to align when there is insufficient shared detail or camera movement. For best results, use several closer overlapping angles of the same unchanged room, with details visible in multiple photos.

If alignment fails, **Help match photo details** lets you mark at least 12 distinct corresponding points in a pair of photos. These are added to automatic matches and passed through geometric verification; they do not guarantee reconstruction. Pointer and keyboard input are supported. **Use a manual layout** retains the editable photo-covered rectangular room as an optional fallback. An optional **Create AI finish** action uses the existing image generator to produce a separate image from the original room photos. Its inferred areas are labeled, and it does not create measured 3D geometry.

For a solid approximate model, choose **AI-assisted**, then **Build AI room layout**. This sends up to the first eight room photos together to OpenAI vision with structured output, validates the floor outline, wall openings, and photo evidence, and saves a Three.js architectural block model. It estimates walls, windows, doors, cabinets, appliances, stairs, and existing large furniture. Orbit, zoom, switch to a top view, hide fixtures or inferred structure, and expand the assumptions and photo evidence. Inferred surfaces are amber; even elements visible in photos have estimated positions and sizes. This mode does not recover camera poses or depth maps, and its dimensions are not measured. It requires `OPENAI_API_KEY` and uses `gpt-6.1-sol`. Requests set `store: false`. The API work runs remotely; the Mac renders the geometry without CUDA, local model weights, or COLMAP. The separate **Create AI finish** action still produces only a 2D image.

Build status and results persist with the room. The client polls progress while a build runs, including across reloads. One reconstruction runs at a time per server, with four CPU threads and a 12-minute total deadline. Cancelling a build stops its child process. A failed rebuild keeps the previous successful result; changes to the input photos mark that result as outdated. A server restart marks an interrupted build as failed on the next status request so it can be retried. Temporary images and feature databases are removed after completion or cancellation.

AI layouts are stored in plan coordinates: facing plan +z, +x is on the right. `toSceneLayout` converts that convention once at the geometry boundary to Three.js's y-up coordinates, including fixture rotation and wall-opening placement. Stored evidence stays unchanged. Orientation regression tests project the actual geometry from opposing photo viewpoints to catch mirrored stairs and doors.

## Secrets

Varlock resolves `OPENAI_API_KEY`, `SESSION_SECRET`, and the OIDC client secret from Bitwarden Secrets Manager. `.env.schema` contains references, never secret values. Supply `BITWARDEN_ACCESS_TOKEN` securely to the process or Railway service. Use a project-scoped machine token. Production uses `varlock run` at boot; secrets are not embedded into the build.

## Development

Node 24+. Install with `npm ci`, then run `npm run dev:local` for a local studio without Bitwarden or login. SQLite data defaults to `.data/`; generation is disabled unless you supply `OPENAI_API_KEY` in your shell. Override `DATA_DIR` or `APP_URL` as needed. When using `tailscale serve`, set `APP_URL` to the exact browser origin (for example, `https://host.tailnet.ts.net:8443`); its hostname is allowed by Vite and mutations require that origin.

For the regular secrets-backed setup, supply `BITWARDEN_ACCESS_TOKEN` and run `npm run dev`. Local mode applies only to the dev server; production authentication is unchanged. Validate with `npm run check`, `npm test`, `npm run lint`, and `npm run fmt:check`. Use `npm run fmt` to format and `npm run build` to build.

Automatic reconstruction requires **COLMAP 4.x** on the server. On macOS, install it with `brew install colmap`; optionally set `COLMAP_BIN` to an executable path before starting the app. The tested Mac uses COLMAP 4.2.1 without GPU support. The app explicitly selects SIFT and SIFT brute-force matching; learned features, neural matchers, and learned calibration are not enabled. Install the same engine in a production container before using automatic reconstruction there; the existing Railway service configuration does not install COLMAP. Sparse CPU reconstruction works without CUDA. COLMAP dense reconstruction requires a separate CUDA-capable worker, which this implementation does not provision. To run the real-engine integration test against a folder of overlapping `.jpeg`, `.png`, or `.webp` photos, use `ROOMFORM_COLMAP_TEST_IMAGES=/absolute/path/to/photos npx vitest run src/lib/colmap-runner.integration.test.ts`. Normal tests mock job execution and test parsing, match import, ownership, cancellation, saved results, and restart recovery.

## Railway

Deploy the repository, mount a persistent volume at `/data`, set `DATA_DIR=/data`, and use one replica. `railway.json` configures build/start and health checks. The app uses SQLite WAL and short synchronous transactions for room changes; image generation happens outside those transactions. A per-user lease prevents overlapping paid generations. Back up the persistent volume before migrating or removing it. Images currently live as SQLite blobs; move them to object storage when usage grows.

## Image generation

For an **AI-assisted 3D room**, orbit/zoom or choose the top view, select which estimated structure and fixtures to show, then **Capture this view → Generate this view**. The capture is a clean JPEG of the WebGL scene at the chosen camera, without controls or labels. It is sent as the first image to the image-generation API, followed by the reconstruction's original source photos in evidence order, selected product/style references, and an optional prior design. The saved architectural layout (walls, openings, fixtures, photo evidence, assumptions) and captured camera/visibility settings accompany the brief, style, physical scale guidance, and scene options. The saved layout replaces the photo-only geometry pre-pass for this path. Source photos supply appearance/evidence; the 3D render supplies camera/layout. Layout proportions and even photo-visible elements' dimensions remain estimates. Inferred regions stay explicitly uncertain; adherence and physical fit are not guaranteed.

Each guided design retains its guide image and a validated layout snapshot, linked to the reconstruction result and input photo/reference IDs. **Compare** compares the guide with the generated design; **3D guide and source evidence** exposes the retained input and architectural constraints, even after a reconstruction rebuild. Deleting the design removes these retained artifacts. The generation boundary checks ownership, the current reconstruction result, source photos, and capture dimensions; changed photos or an in-progress/replaced reconstruction require a fresh capture after rebuilding. **Generate from photo** keeps the existing photo-based path available.

Generation has six modes: **Redesign** (preserve architecture, restyle and refurnish), **Stage** (furnish an empty room), **Paint** (keep furniture and layout, change only colors, finishes, and surfaces), **Empty** (remove furniture, keep the shell), **Sketch** (turn a sketch or 3D-software screenshot into a photorealistic room), and **Freestyle** (compose a room from the type, style, brief, and optional measurements alone — no input photo, with a portrait, landscape, or square output choice). Outdoor room types (Garden, Patio, House exterior, Balcony) switch the prompts to landscape-designer wording that preserves fixed structures, boundaries, paving, and mature plantings instead of interior architecture, and skip the room-geometry pre-pass. Optional scene controls add people or pets (man, woman, couple, family, friends, dog, cat) and set the lighting direction (daylight, golden hour, evening, cozy lamps). Designs can be starred to keep a Saved filter in the filmstrip. Any design can be brush-edited: mark a region, describe the change, and the server sends the image plus a mask to the OpenAI image-edit endpoint, storing the result as a new design (`/api/designs/edit`). A design with a before image can be exported as a five-second crossfade before/after video, recorded entirely client-side. Runs produce 1, 2, 4, or 8 variations in one call; the per-user lease covers the longer runtime for larger batches. Before rendering, a layout pre-pass sends the base photo to a vision model (`OPENAI_LAYOUT_MODEL`, default `gpt-6-luna`) which estimates the room's geometry and returns a placement plan — where each selected product goes and what fraction of the wall it should span given its physical size. The plan is embedded in the image prompt and shown under the design. If the pre-pass fails, generation falls back to prompt-only guidance.

Sizes drive the render: `src/lib/scale.ts` parses product dimensions (`211 × 88 × 83 cm`, `W:84 1/4"`, mm/m/in, fractional inches) and room measurements (`4.2 × 3.6 m, ceiling 2.6 m`), and turns them into scale guidance with real wall ratios. Room measurements are optional, editable per room, and act as the scale authority when present. Output orientation follows the base photo's pixel aspect ratio, read server-side from JPEG headers (`src/lib/image-size.ts`); pixel dimensions are never treated as physical measurements. `OPENAI_IMAGE_MODEL` is configurable. Each run generates 1, 2, or 4 variations in one call; the per-user lease covers the longer runtime for larger batches. Images are resized in the browser before upload.

Product import reads Open Graph, Twitter, structured Product data, and main-page images on public HTTPS pages. Shopify variant links use the selected variant’s product image. Imports also capture structured physical dimensions and Shopify size options. Explicit variant sizes are selected automatically; multiple unselected sizes remain choices. Each reference has an editable physical-size field, which feeds the same scale guidance. Cheerio handles HTML parsing; ipaddr.js rejects non-public IP ranges, and HTTPS requests pin validated DNS results and recheck redirects. Websites that block access or require JavaScript still need an uploaded photo. No general web scraping or automatic Zillow import. AI output is a visualization, not an accurate measurement or a guarantee of product fit.
